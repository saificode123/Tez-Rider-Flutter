# Existing biometric entry: Stage1 policy and Stage3 prerequisites

2026-10-22. Policy applies to existing optional biometric login, not every restored session. Stage3 owns enrollment UI, account binding, lifecycle and platform acceptance.

1. Device authentication is not server authorization. A successful native result must still restore a real Supabase session and pass fr28_account_status, canonical role/approval/block/revocation checks and gated routing. Never trust tr_role or selected role.
2. Existing biometric entry now sets biometricOnly:true. Device PIN/passcode is not an automatic substitute on this entry. Existing email/password login remains the explicit fallback. Recheck enrolled biometrics immediately before prompting; unsupported/no enrollment/cancel/failure denies local unlock. Native fingerprint/FaceID specifics remain untested here; hardware names are not a server guarantee.
3. Existing tr_refresh/tr_role use flutter_secure_storage. No refresh/access tokens, password or CNIC in logs/reports/source. Stage3 must bind opt-in and stored token to canonical account, sync rotation and clear stale drafts/account identity on switch. Current global bio_enabled is not proof of account-specific enrollment.
4. SDK session persistence is separate from the secure-storage convenience copy. Supabase initialization currently uses default persisted SDK restoration. This stage does not claim every SDK session is hardware gated. Before advertising biometric app-lock, Stage3 must select supported secure SDK storage or require local unlock before automatic restoration; do not weaken server checks/offline denial. Normal authenticated session restore remains permitted by FR02/SEC03.
5. Inspect installed gotrue2.27.2 source: signOut defaults local, removes SDK session before remote revoke; remote failure does not itself retain its in-memory session. Existing AuthController additionally removes tr_refresh/tr_role and logged-in flag. Logout presence/push cleanup occurs before signOut; failure in those prerequisites and persistent-storage failure require Stage3 fault-injection verification, not an unconditional offline-logout guarantee.
6. Blocked/revoked/expired sessions must return to sign-in and remove sensitive state; password login never bypasses a server ban. Session lifetime is controlled by the server requirement/approved policy, not biometric success. No raw owner-sensitive media may be made accessible after logout.
7. Stage3 prerequisites: explicit opt-in after valid password/server account; account switch and enrollment-change invalidation; opt-out cleanup; rotation/restoration/logout network failures; background/foreground/cancel/lockout; Android real sensor and iOS/macOS signing/device evidence. Never store passwords to simulate biometrics.

Security change is narrow: enrolled-only biometric request and no implicit device-PIN fallback. Local deterministic tests cover unsupported/no enrollment, requested biometric-only option and cancellation. They do not constitute physical enrollment/login/FaceID acceptance. SEC-A08's original policy mismatch is addressed; remaining optional Stage3 acceptance is tracked separately and is not by itself a Stage1 security blocker.
