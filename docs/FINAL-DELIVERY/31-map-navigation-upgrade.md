# Delivery map and navigation upgrade

2026-10-30, Asia/Karachi. TEST project `igeisilhtmglgnqvllrx` only. This report supplements report 30 and preserves its dated delivery evidence.

## Implemented maps

Customer and Rider maps share a reusable road-map view with distinct pickup, destination and confirmed Rider markers, route outline, ETA/distance, accuracy and last-update age. A 240ms animation interpolates only between confirmed fixes and ends at the received position; it neither predicts travel nor improves the measured publication cadence. Manual panning suspends follow across updates. Recenter resumes follow; route overview fits the available confirmed points. Information panels scroll within bounded space. The physical first-build check exposed a cramped Rider viewport; the final layout reserves at least half the tested screen for the map despite tall existing delivery forms.

Stale, still-authorized Customer positions retain a gray last-known marker and timestamp. Revocation, stop, terminal lifecycle, access denial and account changes clear private tracking state and invalidate pending route responses. Stale fixes cannot claim live ETA. Tile, permission, precision, connectivity and routing failures have feedback/retry states. Android reduced-accuracy permission is explicitly rejected for delivery streaming. English/Urdu, directional layout, large text and reduced-motion behavior use the existing app infrastructure.

Rider navigation uses the existing real location service and consent controls; the widget creates no GPS publisher. Before pickup, an assigned, eligible, online Rider can request road directions to the saved vendor pickup from a fresh matching position. After normal delivery start, navigation targets the confirmed Customer destination and requires existing live-sharing consent. Phase changes invalidate old geometry. Existing checklist, sharing, arrival, proof and contact workflows remain in place. Admin monitoring retains its existing scope and shows consistent fresh-location markers with an initial overview. No new Vendor tracking module was invented.

The existing routing function now supports a validated pickup target, with a separate private pickup cache and the existing shared rate/quota budget, reservation and advisory-lock protections. Only the assigned eligible Rider on a ready order can use pickup routing; Customer/Admin/other-Rider access is denied. Cache cleanup and lifecycle transitions discard geometry without losing settlement of an in-flight quota reservation. No new paid service, dependency or embedded secret was added. Existing free-provider limits still apply; no unlimited production capacity is claimed.
