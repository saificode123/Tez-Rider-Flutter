1 Introduction   
 
 
1.1 System  Introduction  
 
Tez Rider  is a verified,  multi -vendor  delivery  platform  built with Flutter  (Android/iOS 
front -end) and Supabase (PostgreSQL back -end). It connects Customers, Vendors, 
Riders, and Administrators on a unified platform to enable product browsing across 
groceries, medicines, food, and daily essentials; real -time GPS -tracked delivery;  
secure payment ; and a structured  pipeline . It also opens secure delivery channels for 
overseas Pakistanis sending essentials home.  
 
1.2 Background  of the System  
 
Pakistan's e -commerce market is dominated by cash -on-delivery transactions and 
phone -based ordering. Existing platforms such as Foodpanda target food exclusively 
and lack the verification depth for a general goods marketplace. Most local solutions 
use Fire base (NoSQL), which sacrifices relational data integrity and complicates 
financial  reporting  and audit  trails.  Tez Rider  differentiates  itself  by adopting  Supabase 
(PostgreSQL) as the back -end providing full SQL query capability, Row -Level 
Security  (RLS)  policies  for per-user data isolation,  real-time change -data capture,  and 
built-in authentication  within  a single  managed  service.  The Flutter  front -end delivers 
a consistent Android/iOS experience  from  one codebase, while  the REST  + Realtime 
API layer supports future web and third -party integrations.  
 
1.3 Objectives  of the System  
 
• Build a Flutter mobile application serving four distinct roles: 
Customer,  Vendor,  Rider,  and Administrator,  across  groceries, 
medicines, food and daily essentials.  
• Implement a Supabase (PostgreSQL + RLS) back -end for all data 
persistence,  authentication,  real-time GPS updates,  and file storage.  
• Integrate  Maps  API for live  GPS tracking  of Rider  location, route  Software  requirement  and design  specification  for Tez Rider  4  
 
 
calculation,  and ETA  estimation.  
• Enforce  CNIC -based  Rider  verification . 
• Build  a mandatory  delivery  checklist  system  to reduce  incorrect  and damaged  order 
incidents.  
• Provide  a multi -tier dispute -resolution  module  with evidence  upload, 
Admin dispute handling and automated refund triggering.  
• Deliver an Admin analytics dashboard with real -time order 
monitoring,  revenue  reports,  and rider/vendor  performance  KPIs.  
 
1.4 Significance  of the System  
 
Tez Rider  carries  strategic  significance  across  multiple  domains:  
• Empowers  small  and medium  vendors  including  home -based  businesses 
to sell and deliver products digitally without independent logistics

• Gives  Riders an automated, GPS -verified, performance -tracked job

2 Overall Description  
 
 
 
2.1 Product  Perspective  
 
Tez Rider is a self -contained, cloud -native platform operating on a client –server 
model.  The Flutter  mobile  application  communicates  with the Supabase  back -end over 
HTTPS/REST  for standard  operations  and WebSocket  (wss://)  for real-time GPS and 
order -status  streams.  The Supabase  instance  hosts  the PostgreSQL  relational  database, 
GoTrue authentication service, Supabase Storage (product images, delivery proof 
photos), Realtime channels, and the PostgREST API layer with RLS -enforced 
policies.  
External services like Maps API  are integ rated either directly from the Flutter client 
or via Supabase Edge Functions.

2.2 Product  Scope  
 
Tez Rider is a multi -vendor delivery management system that handles the complete 
order lifecycle from customer registration  to final delivery. The system allows users 
to browse  products, manage  cart and place  orders . After  order  placement,  vendors  
process  requests  and CNIC -verified  riders  are assigned for delivery. The system 
provides real -time GPS  to ensure secure and transparent operations.  
The system  also supports  structured  onboarding  for vendors  and riders,  where  vendors 
are verified before listing products and riders are registered using CNIC verification.  
 
Out of scope for the current version:  web-browser customer interface, 
subscription/recurring  orders,  and multi -currency  support.  These  may be addressed  in 
a future release.

2.3 Product  Functionality  
 
The Tez Rider  system  is organized  into ten functional  modules  as defined  in the 
approved FYP proposal:  
 
2.3.1 User  Management  & Authentication  System  
 
• User  registration  for all four roles  (Customer,  Vendor,  Rider,  Admin) 
with JWT token -based authentication via Supabase Auth.  
• Role -based  access  control  (RBAC)  enforced  at both the Flutter  navigation 
layer and the Supabase RLS database layer.  
• User  profile  management:  name,  phone,  email,  address,  avatar,  and role-specific  fields.  
 
2.3.2 Order  Management  & Processing  System  
 
• Multi -category  product  catalogue  browsing  (groceries,  medicines,  food,  daily 
essentials) with search and category filters.  
• Persistent  shopping  cart with multi -vendor  support  — customers  can 
add items from multiple vendors in one cart.  
• Order placement with full status tracking: PENDING → 
ACCEPTED  → IN_TRANSIT  → DELIVERED  / CAN CELLED.  
• Order  history  with per-order  itemized  breakdown and  status timeline.  
 
2.3.3 Real -Time  Tracking  & Delivery  Verification  System  
 
• Live GPS tracking  of Rider  location  streamed  via Supabase  Realtime  every 
2-3 seconds; rendered on a Maps widget with route polyline and ETA.  
• Mandatory  pre-delivery  checklist  for Riders  to reduce  incorrect  or damaged order 
incidents.  Software  requirement  and design  specification  for Tez Rider  7  
 
 
• Mandatory  pre-delivery  checklist  for Riders  to reduce  incorrect  or damaged order 
incidents.  
 
2.3.4 Vendor  Management  & Product  System  
 
• Vendor  registration  with business  name  and address  (subject to Admin 
approval).  
• Full product CRUD: add/edit/delete listings with name, description, 
price,  category,  images,  and stock  quantity  stored  in Supabase  Storage.  
• Inventory  management  with configurable  low-stock  alerts.  
• Order  accept/reject  workflow  with configurable  timeout;  auto-cancellation  on timeout.  
• Vendor  earnings  dashboard  with per-order  transaction  breakdown  and 
aggregate performance analytics.  
 
2.3.5 Rider  Management  & Assignment  System  
 
• Rider  registration with  CNIC  verification  for identity  validation.  
• Availability  toggle  (online/offline)  and location -based  intelligent  assignment 
algorithm via Supabase Edge Function (nearest available verified rider).  
• Delivery  performance  tracking:  completion  rate, average  delivery  time,  customer  rating.  
• Rider  earnings  history  with per-delivery  breakdown.  
 
2.3.6 Feedback,  Rating  & Dispute  Resolution  System  
 
• Dual feedback mechanism: public star ratings (1 –5) for Rider and 
Vendor  displayed  on their profiles,  and private  complaint  submission.

• Automated  blocking  of consistently  low-rated  vendors  or riders  after 
configurable threshold breaches.  
• Running  average  rating  computation  updated  in real time  on Vendor/Rider  profiles.  
 
2.3.7 Admin  Dashboard  & Analytics  System  
 
• Vendor  and Rider  approval/rejection  workflows  with document  review.  
• Real-time order  monitoring  dashboard  with live counts  and map view.  
• Analytics  charts:  daily/weekly  order  volumes,  revenue  trends,  dispute  rates, 
top-performing vendors, rider KPIs.  
• Business  intelligence  reports  exportable  for management review.  
• User  management:  block/unblock  users;  resolve  escalated  disputes.  
 
2.3.8 Notification  & Communication  System  
 
• Multi -channel push notifications for order status changes, rider 
assignment,  dispute  updates,  and Admin  broadcasts.  
• SMS  OTP  delivery  via SMS  Gateway  for delivery  confirmation.  
• Notifications for  order  confirmations,  invoices,  and account  actions.  
 
2.3.9 Security  & Data  Protection  System  
 
• Supabase  RLS policies enforcing  per-user data isolation  at the  PostgreSQL layer.  
• Input  validation and  SQL  injection prevention  on all API endpoints.  
• Audit  logging  of all critical  operations  in a security_audit_log  table.  
 
2.4 Users  and Characteristics  
 
2.4.1 Primary  Users  
 
• Customers are everyday mobile users in urban Pakistan, aged 16 –50, with 
moderate  smartphone  proficiency.  They  require  a simple,  fast UI with support 
for local payment methods, Urdu -friendly navigation, and full delivery 
visibility including rider identity and live G PS. 
• Vendors are small -to-medium business owners including home -based sellers 
with basic smartphone literacy. They need a straightforward dashboard for 
inventory  management,  order  processing,  and earnings  tracking  without  Software  requirement  and design  specification  for Tez Rider  9  
 
 
requiring  technical  knowledge.  
• Riders  are gig workers  operating  in variable -connectivity  environments.  They 
need a lightweight, battery -efficient interface with clear job queues, turn -by-
turn navigation, and simple proof -capture tools. CNIC registration is 
mandatory.  
• Administrators are internal platform operators with higher technical 
proficiency. They inte ract with the platform infrequently but require 
comprehensive moderation tools, real -time monitoring, and analytical 
reporting.  
 
2.4.2 Secondary  Users  
 
• This app doesn’t contain  any secondary  user or supporting  roles.

4.1 Performance  Requirements  
 
The Tez Rider  system  shall  provide  fast and reliable  performance  with quick  API responses, 
smooth screen loading, real -time GPS tracking, efficient payment processing, timely OTP 
delivery, and stable operation for multiple concurrent users without significant performance 
degradation.  
 
4.2 Safety  and Security  Requirements  
 
4.2.1 Safety  Requireme nts 
 
• S-01: The system shall require a confirmation dialogue before any 
destructive  action  (order  cancellation,  account  deletion,  block  user).  
• S-02: If the Rider's  GPS stream  is interrupted  for more  than 30 seconds, 
the Customer's map shall display a 'Location temporarily unavailable' 
message rather than showing a stale pin.  
• S-03: Payment failures shall trigger an immediate rollback  of order status 
to PENDING  and notify  the Customer  within  2 seconds,  with a clear error 
message and retry option.  
• S-04: OTP  entry  shall  allow  a maximum  of 3 attempts;  on failure  the OTP 
expires  and a fresh  one must  be requested,  preventing  brute -force  delivery 
confirmation.  
• S-05: Files  uploaded  to Supabase  Storage  shall  pass validation  (images 
only for proof and CNIC) before being accepted.  
• S-06: Vendor  order  acceptance  timeout  (2-3 minutes  default)  shall 
trigger automated order cancellation and customer notification to 
prevent indefinitely pending orders.  
 
4.2.2 Security  Requirements  
 
• SEC -01: All Supabase database tables shall have Row -Level Security 
(RLS)  policies  ensuring  each user can only access  record s they own or are 
authorized to access by their role.  
• SEC -02: User  passwords  shall  be hashed  by Supabase  GoTrue;  plain -text 
passwords shall never be stored or logged.  
• SEC -03: JWT  access  tokens  shall  expire  after 1 hour;  refresh  tokens after Software  requirement  and design  specification  for Tez Rider  31  
 
 
7 days.  Silent  refresh  is managed  by the supabase_flutter  SDK.  
• SEC -04: All API keys (Supabase anon key, Maps key, payment 
credentials)  shall  be stored  as Flutter  --dart-define  environment  variables  or 
Supabase Vault secrets; never hard -coded or committed to version control.  
• SEC -05: Payment  gateway  callbacks  shall  be authenticated  via signature 
validation before any order -state mutation.  
• SEC -06: Rate limiting  (max  100 requests/minute  per authenticated  user) 
shall be enforced at the Supabase API Gateway layer.  
• SEC -07: All critical Admin actions shall be written to 
security_audit_log  with actor_id,  action,  target_type,  target_id,  and 
created_at.  
• SEC -08: Supabase  Storage  media files shall  be served  exclusively  via 
time-limited  signed  URLs  (15-minute  TTL)  to prevent  hotlinking  and 
unauthorised access.  
• SEC -09: CNIC  data shall  be stored  encrypted  and displayed  in masked 
form (3***0 -******* -*) at all customer -facing endpoints.  
• SEC -10: All user-supplied  inputs  shall  be validated  and sanitised  in 
Supabase Edge Functions to prevent SQL injection, XSS, and 
malformed -request attacks.  
 
 
4.3 Software  Quality  Attributes  
 
4.3.1 Reliability  
 
Supabase managed infrastructure provides a 99.9% uptime SLA with automatic 
failover. The Flutter app implements optimistic UI updates with automatic retry on 
network failure (exponential back -off), ensuring graceful degradation in low -
connectivity environm ents common in Pakistan.  
 
4.3.2 Usability  
 
Onboarding flows are designed to achieve Time -to-First-Order under 3 minutes for 
new Customers. Rider -facing screens prioritize large buttons and minimal text to 
support variable literacy levels.  
 
4.3.3 Maintainability  
 
The Flutter  codebase  follows  Clean  Architecture (presentation  / domain  / data layers)  Software  requirement  and design  specification  for Tez Rider  32  
 
 
with feature -based folder structure. Supabase database schema changes are managed 
exclusively through versioned migration files; no direct production schema 
modifications  are permitted.  All business  logic  resides  in Riverpod  providers  (testable 
without UI) and Supabase Edge Functions.  
 
4.3.4 Portability  
 
Flutter's single codebase targets Android and iOS without platform -specific 
modifications.  Supabase can be self -hosted or migrated to any  cloud provider (AWS, 
GCP, Azure) by updating only two  environment variables (SUPABASE_URL, 
SUPABASE_ANON_KEY). No vendor lock -in exists  at the data layer since 
PostgreSQL is a fully open standard.  
 
4.3.5 Scalability  
 
The stateless PostgREST API layer scales horizontally behind a load balancer. 
Supabase Realtime's distributed channel architecture supports millions of concurrent 
WebSocket subscribers. Edge Functions scale independently on Deno Deploy 
infrastructure.  
 
4.3.6 Testability  
 
Each  Riverpod  provider  is unit-tested  with riverpod_test  using  a mock  Supabase  client. 
Supabase  Edge  Functions  are unit-tested  with Deno's  built-in test runner  against  a local 
Supabase Docker stack. Flutter integration tests use flutter_test with an in -memory 
fake repository layer. Target code coverage: ≥ 80% for the domain and data layers.  
 
4.3.7 Interoperability  
 
Supabase exposes a fully  standard PostgREST API, meaning any  HTTP client future 
web dashboards, third -party analytics tools, or ERP systems can query the platform. 
All payment integrations use vendor -standard REST APIs with no proprietary SDKs 
that would block future gateway switching.  
 
4.3.8 Adaptability  
 
The relational  SQL  schema  allows  clean,  versioned  migrations  as requirements  grow.  Adding  a 
new user role requires only a new role enum value, updated RLS policies, and a Flutter role 
navigator.  The modular architecture  allows  modules  to be enhanced  or replaced  independe ntly. Software  requirement  and design  specification  for Tez Rider  33
